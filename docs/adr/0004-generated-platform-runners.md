# ADR 0004 — Generate Flutter platform runners instead of committing them

- Status: Accepted
- Date: 2026-08-19

## Context

Flutter platform runner directories contain a large amount of framework-generated boilerplate. Committing runners can make repository diffs noisy and allows old generated files to drift away from the Flutter SDK actually used by CI or a contributor.

Countora still needs deterministic project-specific platform configuration, especially Android notification permissions/receivers and core-library desugaring.

## Decision

Do not commit generated `android/`, `ios/`, `web/`, `windows/`, `macos/`, or `linux/` runner directories.

Generate them with:

```bash
dart run tool/bootstrap_platforms.dart
```

The script invokes `flutter create` with Countora's project name/organization and then applies idempotent Countora-specific Android patches.

CI and release workflows always generate runners before dependency resolution, analysis, tests, or builds.

## Consequences

### Positive

- runner boilerplate matches the installed Flutter SDK;
- repository history emphasizes Countora-owned code;
- generated platform drift is reduced;
- Android customizations remain reviewable in one deterministic script.

### Trade-offs

- a working Flutter SDK is required before native runners appear locally;
- platform-specific customizations must be encoded in bootstrap logic rather than edited only in generated files;
- release builds must prove the bootstrap process remains compatible with current Flutter templates.

## Rule for future native customizations

Any required native change must be either:

1. generated by `tool/bootstrap_platforms.dart` idempotently; or
2. represented by a small Countora-owned source/template copied by the bootstrap process.

Do not depend on an untracked manual edit inside a generated runner.
